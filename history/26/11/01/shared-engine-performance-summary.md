# 스크롤·Date picker·lazy load가 함께 빨라진 이유

2026-11-01에 적용한 수정의 설명을 2026-11-02에 추가했다.
사용자는 "스크롤이랑 date picker, lazy load가 굉장히 부드럽고 빨라졌다"고 보고했다.
이 문서는 기존 코드·측정·사용자 확인을 정리한 후속 기록이며 새 성능 검증 결과는 아니다.

핵심은 **위젯을 생성·갱신·제거할 때 공통으로 걸리던 엔진 비용을 줄인 것**이다.
스크롤 중 새 항목을 표시하거나, 다음 달의 날짜 셀을 만들거나, lazy load로 여러 위젯을
구성할 때 같은 경로를 사용하므로 개선 효과가 여러 화면에 함께 나타날 수 있다.

## 마지막 공통 엔진 수정

### 의존성 등록·검색·해제의 병목 제거

위젯은 테마·글꼴·화면 환경 같은 상속 정보를 사용하면서 `InheritedElement`에 의존성을
등록한다. 기존 저장소는 선형 `DartMap`이어서 항목을 찾을 때 목록을 훑고, 제거할 때는
뒤의 항목을 이동했다. 위젯이 많이 생기고 사라지면 이 작업이 반복됐다.

[현재 구현](../../../../Doroti/src/Doroti.Framework.Widgets/framework.cs)은 해시 검색과
연결 목록으로 의존성을 관리한다. 검색·등록·해제에서 전체 목록 순회를 피하면서 알림 순서,
제거 후 재등록 순서와 알림 중 목록 변경에 대한 snapshot 동작을 보존한다.

512개 의존성에서 20회 검색하는 회귀 검사의 Element 비교 횟수는 **10,240회 → 20회**였다.
이는 의존성 검색의 비교 횟수이며 전체 UI가 같은 비율로 빨라졌다는 뜻은 아니다.
날짜 셀, 새 목록 행, 화면에서 제거되는 항목의 의존성 처리 비용을 함께 줄이는 수정이다.

### 중복 실행 컨텍스트 생성 축소

각 컴포넌트의 rebuild는 뷰 호출 범위에 진입한다. 기존에는 같은 뷰 안에서도 애플리케이션
콜백 범위와 뷰 콜백 범위를 차례로 만들며 콜백 객체와 `AsyncLocal` 맵을 반복 교체했다.

[실행 컨텍스트](../../../../Doroti/src/Doroti.Runtime/DorotiExecutionContext.cs)와
[뷰 호출 범위](../../../../Doroti/src/Doroti.Ui/PlatformDispatcher.cs)는 같은 콜백 큐·취소 토큰의
중첩 호출과 동일 시간 공급자를 재사용하고 최종 뷰의 범위로 바로 진입한다.
[플랫폼 환경](../../../../Doroti/src/Doroti.Ui/ViewContracts.cs)도 동일 인스턴스이면 중복 범위를
만들지 않는다. 다른 뷰·취소 범위·외부 override로의 전환과 복원은 유지한다.

같은 뷰에 20회 중첩 진입하는 검사의 할당량은 **27,200 → 5,440바이트**, 80% 줄었다.
위젯을 많이 구성할 때 만드는 임시 객체가 줄어 GC 부담을 낮추는 변경이다.
할당량 감소율을 GC 정지 시간의 감소율로 해석하지 않는다.

## 세 동작에 함께 영향을 주는 경로

| 동작 | 공통 엔진에서 수행하는 작업 | 개선과의 연결 |
| --- | --- | --- |
| 스크롤 | 새 행 생성, 위젯 갱신, 화면 밖 항목의 의존성 해제 및 캐시 이동 | 등록·해제와 반복 호출 비용 감소 |
| Date picker | 다음 달의 날짜 셀 생성, 기존 월 갱신·해제 | 월 전환 중 UI 처리 지연 감소를 직접 비교 |
| lazy load | 필요해진 항목의 위젯 생성과 의존성 등록 | 여러 위젯을 한꺼번에 구성하는 비용 감소로 설명 가능 |

사용자는 세 동작의 개선을 함께 확인했다. lazy load 자체의 개선폭은 별도로 분리 계측하지
않았으므로, 그 효과의 원인 설명은 공통 코드 경로에 근거한 해석이다.

Windows의 동일한 6회 월 전환 비교에서는 **전환별 최대 UI 처리 시간의 평균이
75.673 → 19.009ms**, 74.88% 감소했다. 이 값은 UI owner의 wall time이며 표시 FPS나
전체 앱의 60/120Hz 성능 보증이 아니다. 첫 전환의 33ms와 일부 GC pause는 남아 있었다.
사용자는 Windows 월 전환에 대해서도 별도로 "부드러워졌음"이라고 확인했다.

[Date picker 상세 기록](date-picker-month-transition.md)과
[수치·검증·소스/바이너리 식별](date-picker-month-transition-results.json)에 근거를 남겼다.
달별 지연 생성 구조와 전환 시간은 유지했으며, 최종 변경에 달력 위젯 전용 캐시는 없다.

## 함께 적용된 앞선 스크롤 수정

- 닫힌 그리기 명령과 path·텍스트 기록의 재사용으로 반복 복사와 할당을 줄였다.
- 같은 부모·owner 안에서 `RenderSectionList`의 keep-alive 항목을 옮길 때 연결과 parentData를
  유지한다. 캐시 이동마다 전체 하위 트리를 detach/attach하던 작업을 줄였다.
- Windows의 매 프레임 장면 검사를 인덱스 순회로 바꿔 closure·열거자 할당을 줄이고,
  MAUI 접근성 자식의 참조·순서가 같으면 기존 peer 목록을 재사용한다.
- Android에서는 살아 있는 뷰의 GPU context 유지와 Surface 교체를 분리하고,
  native 프레임·입력 콜백의 참조 수명을 정리해 복귀 후 콜백·GC bridge 부담을 줄였다.

합쳐 하나의 통제된 전후 비교로 사용하지 않는다. 자세한 범위와 미확인 항목은

[공통 녹화·캐시 이동 후속](android-resume-inertia-followup.md),
[Windows 검토](windows-resume-scroll-review.md)에 보존한다.
