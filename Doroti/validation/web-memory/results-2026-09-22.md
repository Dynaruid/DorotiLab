## 구현과 소유권

1. **M1:** `doroti.web.policy.ts`에서 요청·선택·이유·메모리 프로필을 한 번 계산해 loader → host → Worker로 전달한다. iPhone/iPad/iPod 및 desktop-UA iPad 자동 선택은 WebGL이며 다른 플랫폼은 기존 WebGPU 기본값이다. 명시 override는 유지한다. 초기화 실패를 다른 backend로 숨기지 않으며 새 hot fallback/reload 경로를 넣지 않았다. DOM dataset과 bootstrap context, Worker 경계 snapshot에서 선택 이유를 확인할 수 있다.
2. **M2:** owner의 `_paintGate` 아래 256-entry LRU. 다음 lookup 전에 이전 draw/layout 사용이 끝나는 기존 호출 구조를 유지한다. paint/font를 복사·참조하는 native picture/recording은 독립 native 수명을 가진다. 등록 font 변경은 generation 증가 및 text/command/raster 캐시 무효화로 처리한다. renderer Dispose가 남은 항목을 해제한다. 코드포인트 lookup memo도 항목당 512개로 제한하되, 실행 중인 text run의 font는 해제하지 않는다.
3. **M3:** mobile WebGL은 native 64MiB, raster 24 entries / 4M pixels(16MiB RGBA8). WebGPU와 desktop은 기존 native 256MiB 및 raster 16M pixels(64MiB RGBA8)를 유지한다. WebGPU의 작은 예산 후보는 지연 결과가 일관되지 않고 실제 native working set도 설정값 아래로 줄지 않아 채택하지 않았다. 추가 surface를 만들기 전에 예산을 예약하고, 현재 프레임에서 사용한 캐시 항목은 보호한다. 한 그림은 전체 pixel 예산의 1/4 이하만 차지한다. 수용할 수 없는 그림은 정상 명령 재생 경로를 쓴다. 마지막 렌더링 이후 5초 이상 유휴일 때 owner의 프레임 사이에서 native unused cleanup을 수행한다. 활동 중에 주기적으로 회수하던 후보는 최종 소스에 남기지 않았다. GPU queue를 동기화하거나 active recording/map/texture를 강제로 해제하지 않는다.
4. **M4:** mobile 최초·성장 backing은 실제 필요 픽셀 크기. 면적 초과 ≥25%, 크기 안정 1초, 마지막 재할당 후 2초 조건으로 축소한다. 축소할 축부터 변경해 회전 중 불필요한 정사각형 중간 버퍼를 피한다. Worker만 transferred canvas 크기를 수정하며 기존 admission/commit 경로로 결과를 전달한다. DPR·widget state·효과는 변경하지 않는다.

Text bytes는 wrapper/map의 명시적 추정치이며 font 파일·공유 typeface·native glyph cache·resident bytes를 포함하지 않는다. Raster bytes는 소유 image 픽셀의 RGBA8 환산이다. canvas old+new 추정치도 depth/stencil, browser buffering, pending GPU reference와 driver allocation을 포함하지 않는다. WASM capacity를 live/resident memory와 동일시하지 않는다.

설치된 API 확인 결과 Graphite context 사용량은 노출되지만 recorder 사용량은 노출되지 않아 `notMeasured`로 기록한다. context와 recorder는 각 예산을 가지며 실제 중복 포함 여부를 알 수 없는 수치를 총 GPU 메모리로 합산하지 않는다. 설치 패키지 commit `143a933a753dbfeca1909524b2c06c546c5c3e20`의 [SKGraphiteImageCache](https://github.com/mono/SkiaSharp/blob/143a933a753dbfeca1909524b2c06c546c5c3e20/binding/SkiaSharp/Gpu/Graphite/SKGraphiteImageCache.cs)는 이미 256-entry LRU와 native reference 계약을 구현한다. 이를 무제한 누수로 가정해 교체하지 않았다. [Skia recorder API](https://skia.googlesource.com/skia/+/refs/heads/main/include/gpu/graphite/Recorder.h)와 설치 managed API를 구분했다.

### 같은 backend의 비교

WebGL 재조정 후보(최종 유휴 조건 보강 전)의 warm visit 두 구간을 합친 Framework p95:

| --- | ---: | ---: | ---: |
| 08 → 07 (BA) | 36.54 | 23.94 | −34.5% |
| 09 → 10 (AB) | 39.31 | 24.81 | −36.9% |
| 11 → 12 (AB) | 34.91 | 25.29 | −27.6% |

이는 선택된 workload의 동기 owner 처리 지표이며 물리 입력 지연이나 P0~P5 전체 성능 목표 충족을 뜻하지 않는다. M2~M4 통합 후보의 결과이며 각 정책의 CPU 효과를 분리한 수치도 아니다.

WebGPU 작은 예산 후보는 13/14 쌍에서 **14.17 → 26.89ms**, 15/16 쌍에서는 **14.81 → 12.66ms**로 일관되지 않았다. Graphite context의 보고 사용량은 약 **144~155MiB**로 host가 설정한 64MiB보다 컸다. 따라서 작은 Graphite 예산의 안정성·성능 개선 PASS를 주장하지 않고 기존 예산을 복구한 최종 경로를 별도로 검증한다.

sample의 text entries는 일부 짧은 실행에서 80→116→122 또는 80→80→119로 증가했다. 이 실행들을 수렴 PASS로 처리하지 않는다. 분석기는 `stable`, `nonDecreasingWithGrowth`, `strictlyIncreasing`을 구분한다. 보유 상한은 초과 native fixture로 검증했으며 긴 반복 검증에서 실제 마지막 세 구간도 별도로 확인한다.
