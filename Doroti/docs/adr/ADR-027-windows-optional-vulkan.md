# ADR-027: Experimental optional Silk.NET Vulkan presenter

- Status: Experimental
- Date: 2026-09-02
- Last updated: 2026-09-04

## Decision

The Windows App SDK `HwndExactCpp` target keeps managed hardware-D3D11 ANGLE/EGL as its default presenter. `DOROTI_WINDOWS_PRESENTER=Vulkan` explicitly selects a separate direct Vulkan/Skia presenter; there is no automatic Vulkan-to-ANGLE fallback. On Windows 11 24H2+, an explicit Vulkan selection may be combined with `WindowBackdropMode.experimentalAcrylic`. That combination preserves the Vulkan presenter and fails explicitly if its Desktop Acrylic target cannot attach; it never substitutes the ANGLE ContentIsland presenter.

The product resolves only the System32 `vulkan-1.dll`, rejects software devices, and requires Vulkan 1.1, a graphics queue, a valid Windows adapter LUID, and importable dedicated D3D11-texture external memory (`VK_KHR_external_memory`, `VK_KHR_external_memory_win32`, `VK_KHR_get_memory_requirements2`, and `VK_KHR_dedicated_allocation`). The current product presenter owns zero Vulkan WSI swapchains; `VK_KHR_surface`, `VK_KHR_win32_surface`, and `VK_KHR_swapchain` are exercised only by separate legacy WSI evidence. If exactly one device satisfies the complete product contract it is selected; multiple capable devices require `DOROTI_WINDOWS_VULKAN_DEVICE` to be an exact or unique device-name fragment.

## Ownership and synchronization

Skia paints a capacity-size wrapper over a grow-only, bounded device-local Vulkan backing image. The complete retained capacity is initialized with application-owned pixels while scene drawing is clipped to the current logical viewport, so newly exposed pixels do not require scene scaling. The presenter copies from that backing into one of three exact-LUID D3D11 shared textures imported as dedicated Vulkan external memory. Copy-fence completion is confirmed before the native Windows Presentation API commit, and each Presentation buffer's availability event is the reuse and teardown authority. If a grown allocation exceeds the retention bound or returns host/device OOM, it is discarded before submission and the exact requested extent is tried once.

The product presenter rejects stale work before selecting an available Presentation buffer. Once selected, it completes the Vulkan copy and commits that same slot to Windows Presentation; there is no visible-HWND WSI acquire/present transaction. A negative or indeterminate Presentation result poisons the manager rather than pretending that buffer ownership is known. Device loss abandons the Skia context before renderer wrappers and native Vulkan handles are released. The legacy WSI qualification remains isolated and does not define product presentation ownership.

Visible Vulkan content is owned by a native topmost DirectComposition target created directly for the top-level HWND. The native child HWND remains hidden bootstrap/storage infrastructure and has no visible geometry timeline. Each retained backing is larger than the exact viewport and is completely refreshed with app-owned pixels. `IPresentationManager::Present` commits the selected full-capacity buffer with an identity transform; the top-level HWND client clip is the only exact-viewport owner.

Resize ordering accounts for screen-origin changes. `WM_SIZING` only ensures retained capacity and never exposes a proposed layout. Actual `WM_SIZE` is the metrics authority. For `Left`, `Top`, `TopLeft`, `TopRight`, and `BottomLeft`, the current top-level raster moves in the same HWND transaction while the raster worker coalesces running work to one latest actual generation; interactive steps do not block USER32 on Vulkan or a CompositionFrame. `WM_EXITSIZEMOVE` performs one bounded exact settle. Fixed-origin `Right`, `Bottom`, and `BottomRight` keep their bounded actual-size terminal/CompositionFrame handshake. This uses no child-window correction, source translation, fixed FPS timer, or stretch.

The native/managed ABI remains GPU-pointer-free. Opaque Vulkan and Vulkan+Acrylic share the same native top raster target. Vulkan+Acrylic creates a non-topmost `Windows.UI.Composition.DesktopWindowTarget` on a dedicated system DispatcherQueue thread, calls `DesktopAcrylicController.SetTarget(WindowId, CompositionTarget)`, enables `DWMWA_USE_HOSTBACKDROPBRUSH`, and switches the native topmost Presentation surface to premultiplied alpha. The explicit mode requires the backdrop target, DesktopWindowTarget, active controller state, host-backdrop attribute, and premultiplied Vulkan surface; it neither degrades to plain transparency nor silently selects ANGLE. Kind, theme, tint, and luminosity options are applied to that controller with the shared last-wins option contract. No ContentIsland is created for the Vulkan topology.

SkiaSharp packages are pinned together at `4.152.0-rc.1.26426.14`. The Windows host directly references `SkiaSharp.Vulkan.Silk.NET` and constructs Skia's Vulkan backend through `GRSilkNetBackendContext` plus the typed `GRVkExtensions.Initialize` procedure callback instead of assembling the generic raw-handle context locally.

## Evidence and promotion boundary

The initial 2026-09-02 run passed package/loader capability checks, a short real-WSI qualification, actual `OUT_OF_DATE`/`SUBOPTIMAL`/`SURFACE_LOST`/`DEVICE_LOST` branch injection and recovery, exact resize/device-reset/minimize-restore/start-close ten-cycle gates, automated input/IME/UIA transport, default ANGLE regression, and self-contained empty-PATH launch on an NVIDIA GeForce RTX 4060 Laptop GPU. An `ANGLE → Vulkan → ANGLE` WGC sequence and all eight borders/corners at 600 px/600 ms reverse motion passed three consecutive runs without marker regressions, device/surface loss, or an outstanding acquired image. That validator did not yet enforce receipt-to-terminal cadence or target-to-present latency, so the result is not reused as smooth-resize acceptance.

After adopting acquire-as-presentation-commit, the AMD Radeon 780M on the same machine passed the maintenance-free capability and real-WSI contracts, product validation, and a Release DorotiDemoApp smoke run. The former exact-child/exact-swapchain design preserved one-to-one generations but repeatedly failed the strict same-run ANGLE latency gate: target-to-present p95 was 25.93 ms against a 20.31 ms allowance, and a hardened repeat reached 39.51 ms after a 96 ms swapchain-create outlier. Those failures remain historical evidence rather than being reclassified.

The 2026-09-03 retained oversized-child design removed swapchain recreation from normal in-capacity resize. A 10-cycle product run reported logical viewport 950x670 inside a 1280x752 surface, one surface creation, nine retained-surface reuses, ten accepted/presented generations, and zero out-of-date/device/surface-loss results. A source-stable `ANGLE → Vulkan → ANGLE` run of all eight borders/corners, three 600 px/600 ms reverse passes each, passed 24/24 automated cases with zero blank frames or Vulkan errors, one surface creation per process, 2,140 retained reuses, at least 119.15 presentations/s during motion, target-to-present p95 at most 4.95 ms, and maximum at most 9.00 ms. This is `PASS-automated-partial`, not physical scan-out or human-drag acceptance. The separate lifecycle qualification passed capability/WSI/product, actual result injection, reset/minimize/resize/start-close gates and source-to-binary correspondence. Hardened reruns use fresh output plus a repository-global single-writer lock and compare start/end HEAD, complete tracked diff, untracked files, key sources, product EXE+IL, probe EXE+IL, managed/native host, and observer identities as applicable.

Physical testing after that run reported transient black/white regions and delayed raster fitting, with visible internal jitter during left/top resize. That observation supersedes any inference of physical acceptance from the earlier automation. The proposed-size admission change addresses the remaining phase mismatch between an origin-moving top-level geometry transaction and the next logical-layout frame. Its final source-locked AMD strict run again passed all 24 edge/corner cases: 1,140/1,140 motion targets were presented with zero supersedes, platform-wait timeouts, or marker regressions, minimum presentation rate was 77.75 Hz, and worst target-to-present p95/maximum were 14.54/16.65 ms. The lower rate than the unconstrained retained-surface run reflects DWM admission pacing, not a hard FPS cap. Capability/real-WSI/product, five injected result branches, reset/minimize/resize/start-close repetitions also passed after making the lifecycle smoke advance only when USER32's actual iconic state matched the requested transition. This remains `PASS-automated-partial`; post-change human border resize and physical scan-out are `notVerified`.

A second physical check found the proposed-size change slightly better but still showed black/white regions. An intermediate revision moved its `DwmFlush` from the matching `WM_SIZE` into a successful `WM_SIZING` prepare, but the following physical check still failed and that provisional path has now been removed. Doroti deliberately does not paint an app-colored parent fallback: doing so would conceal rather than eliminate a top/child exposure. Iteration validation is intentionally focused: the default script now runs left and top-left once, `-Probe` runs top-left once, and the previous 24-case repetition requires `-FullEightEdgeMatrix`. A clean one-case AMD `TopLeft` probe of the actual-size blocking revision passed with 31 accepted motion targets, 32 presented motion terminals, zero platform-wait timeouts, and zero marker regressions. This remains automated partial evidence; current physical behavior is still `notVerified` until direct recheck.

The pre-geometry revision still failed direct physical inspection. Flutter's current Windows embedder instead marks resize started from the actual size, sends metrics, and blocks the platform thread for up to 100 ms while polling its task runner; the raster thread recreates/updates the exact surface and `OnFramePresented` marks the resize done before calling `DwmFlush`. Doroti now follows that actual-size blocking point while retaining its oversized Vulkan child to avoid AMD's per-step swapchain recreation. The former `WM_SIZING` prepare state and 16 ms wait are removed. No parent-color masking is present. The focused automated probe passes, but post-change physical live resize remains to be checked directly.

Timing diagnostics attributed the old AMD limit to `vkCreateSwapchainKHR`, normally about 19–25 ms for each exact extent. The retained child surface moves that cost to the hidden initial create and rare capacity growth instead of paying it for every viewport change. On the tested 1280x752 capacity the initial create took roughly 100–150 ms before first show; memory/startup cost on larger monitors and capacity growth across DPI/monitor changes remain matrix items, not assumed successes.

There are two independent specification boundaries. First, Khronos documents that unextended `vkQueueWaitIdle`/`vkDeviceWaitIdle` does not strictly prove that presentation resources are retired. This AMD device does not expose `VK_EXT_swapchain_maintenance1`, so the current practical queue-idle retirement remains `notVerified` at the specification level even though the automated lifecycle suite passes. Second, SkiaSharp does not expose Skia's Vulkan backend-layout query/update API. After fixing the acquire/layout barrier, an external synchronization-validation run positively proved loader insertion of `VK_LAYER_KHRONOS_validation` and emitted zero validation warning/error messages for the current validation-product workload; arbitrary-workload layout ownership remains unproven. These limits are additional reasons not to promote this presenter.

Slow/medium/fast × expand/shrink/reverse full Cartesian resize, per-edge ten-second stress, long WSI soak, human border resize, physical scan-out, the full GPU/driver/DPI/refresh matrix, physical Korean IME, and accessibility acceptance remain `notVerified` or `notRun`. Until those gates pass, Vulkan is experimental optional and must not become the default.

## 2026-09-03 direction-aware resize and Vulkan Acrylic amendment

A later physical report found that right/bottom resize felt good while left/top resize still made the inner raster appear to shake. The causal difference is the screen origin: the pre-geometry gate displayed the proposed logical layout while an origin-moving HWND was still at its old location, after which USER32 moved the complete window. The content therefore appeared to move once inside the old window and again with the committed window origin. The current direction split above removes that double movement while retaining the lower-latency gate where the origin is fixed.

A final source-built AMD Radeon 780M focused run passed both `Left` and `TopLeft` 600 ms reverse cases. They reported 27/25 outer changes, 26/24 presented motion terminals, 44.57/42.04 presentations/s, zero validation-background gap frames, exact final geometry, zero CompositionFrame waits/timeouts on the post-geometry path, no device loss, and stable source/repository/binary endpoints. A separate 24-case run proved the requested direction split and all transport/final-exact/resource contracts, but its aggregate status is intentionally `FAIL`: the trailing ANGLE reference capture failed one pixel-coverage frame, invalidating every relative cadence comparison, and 11 Vulkan cases reported at least one WGC pixel-coverage failure. This does not qualify the full matrix.

The superseded separate-target Vulkan+Acrylic revision passed its structural counters with no ContentIsland, three Presentation buffers, premultiplied alpha, 500/500 runtime option terminals with zero failures, clean shutdown, one Vulkan device reset, and minimize/restore. A headed DorotiDemoApp run also displayed material content, but the user's following check found plain transparency and remaining resize jitter. Those results are historical evidence only and do not qualify the current architecture.

## 2026-09-03 native top-target and SkiaSharp RC1 amendment

The direction-only revision above did not pass the user's next physical check, and its child-HWND Vulkan raster over a separate top-level Acrylic target produced plain transparency instead of convincing Acrylic. Those statements are retained as history, not current architecture. The current implementation is the top-level native DirectComposition raster target, atomic Presentation viewport transform, grow/shrink-ordered design in the ownership section.

Three consecutive focused AMD Radeon 780M runs of the native top-target revision passed `Left` and `TopLeft` reverse 600 ms cases with zero validation-background gaps, monotonic visible generation markers, final exact geometry, and clean resources. The targeted `TopRight` rerun also passed after the validation product added a right-edge background sentinel; this prevents valid foreground clipped at the minimum width from being mislabeled as a short composition surface. This is automated partial evidence, not physical smoothness acceptance.

The separate-target capability and capture above are historical because the user still observed plain transparency. Physical blur quality and a fresh human left/top drag remain `notVerified`.

## 2026-09-03 post-geometry and DWM-system-Acrylic amendment

The edge-translated native target revision also failed the user's next physical check. It has been replaced by a full-capacity identity Presentation source attached to the top-level HWND. Moving-origin edges defer their actual raster until default `WM_WINDOWPOSCHANGED` processing and a DWM geometry boundary have completed; the matching Presentation then observes its own CompositionFrame before its resize terminal is released.

Six consecutive source-built AMD Radeon 780M `TopLeft` reverse 600 ms runs passed with zero visible-generation regressions, validation-background gaps, or failed terminals. Separate `Left` and fixed-origin `Right` runs also passed. The current artifacts are under `.doroti/evidence/windows-vulkan-top-level-postgeometry-*-20260903`. These are automated capture/transport results, not a claim of physical smoothness.

Vulkan Acrylic now uses the top-level DWM transient-window system backdrop rather than a separate `DesktopAcrylicController` target. The current capability artifact at `.doroti/evidence/windows-vulkan-top-level-dwm-acrylic-capability-20260903/manifest.json` passes and records `DwmSystemBackdrop`, `TransientWindow`, redirection-bitmap alpha enabled, premultiplied Vulkan alpha, and three Presentation buffers. A current-monitor DorotiDemoApp frame at `.doroti/evidence/vulkan-dwm-acrylic-demo-20260903.monitor-frames/monitor-000160.png` visibly suppresses the sharp uncovered-wallpaper structure, while human material quality remains `notVerified`.

The repository package graph is pinned to `4.152.0-rc.1.26426.14`. The Windows presenter uses the same-version `SkiaSharp.Vulkan.Silk.NET` adapter and its `GRSilkNetBackendContext`; a force-evaluated restore of the full product solution succeeded across Windows, Web, Linux, Android, iOS, and macOS targets.

## 2026-09-04 top-level current/latest and Desktop Acrylic amendment

The synchronous post-geometry revision and its DWM transient-backdrop transport did not pass the user's next physical check. They remain historical evidence only. A subsequent parent-local retained-child trial proved the remaining ownership defect: even with a full-capacity identity source and synchronous child background paint, one `TopLeft` capture exposed 18 pixels of real wallpaper between the new top-level client and the previous child subtree. The product now attaches the native topmost DirectComposition target directly to the top-level HWND and keeps the native child hidden as capacity infrastructure. The HWND client and visible raster therefore have one geometry timeline.

Moving-origin interactive resize now keeps that current top-level raster attached while the worker coalesces to the latest actual `WM_SIZE` generation. It does not wait on each Vulkan copy or CompositionFrame; the final exit generation still settles synchronously. Three consecutive `TopLeft` reverse-600 ms runs passed with zero background gaps, marker regressions, timeouts, or device loss. The source-built run delivered 89 motion presents across 94 outer changes at 151.49 presentations/s with 7.65 ms accepted-to-next-present p95. Separate `Left` and `Right` regressions also passed; the fixed-origin `Right` case retained 53 successful CompositionFrame waits and zero timeouts.

Vulkan Acrylic now uses the documented `DesktopAcrylicController.SetTarget(WindowId, CompositionTarget)` Win32 path. A dedicated DispatcherQueue thread owns a non-topmost `DesktopWindowTarget`, the HWND has host-backdrop brush enabled, and the native topmost Vulkan target remains premultiplied above it. The final capability artifact at `.doroti/evidence/windows-vulkan-top-level-acrylic-capability-final-20260904/manifest.json` passed with controller state `Active`, all required target/host flags, three Presentation buffers, zero active WSI swapchains, and the complete reset/lifecycle/product package graph. A new Desktop Duplication capture at `.doroti/evidence/windows-vulkan-top-level-acrylic-visual-final-20260904` shows the sharp external wallpaper detail diffused beneath the Material surface. Physical drag smoothness, physical material quality, and the untested GPU/DPI/refresh matrix remain `notVerified`.
