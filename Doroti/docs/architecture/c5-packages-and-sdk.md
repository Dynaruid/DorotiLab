# C5 real packages and R10 SDK

C5 accepts machine-independent `package:` inputs and resolves them through the committed Flutter pilot lockfile. The full `dart pub deps --json` graph and raw import/export/part/conditional directives enter migration IR; Pub resolution failure is a hard conversion failure. Pub Cache paths never enter IR, diagnostics, source maps, or release reports.

Every generated package carries the compiler, analyzer, Flutter revision, IR, rule-set, emitter and FlutterCompat identities; selected-input hashes; source version and license hash; deterministic generated hashes; diagnostics; migration IR; and Dart-to-C# source map. A and B packages compile without a Dart SDK or compiler after generation. Tier C emits a public consumer-supplied port and `DOTCONV540`; it never emits a no-op plugin.

The executable pilots are `collection 1.19.1` and `vector_math 2.2.0` (tier A), `provider 6.1.5` (tier B), and `shared_preferences 2.5.3` (tier C diagnostic). P4 gives each candidate a `doroti.port/v1` entrypoint and packages the composed `effective/` project. The consumer therefore executes the collection extension, provider replacement, and shared-preferences platform implementation instead of validating only the raw generated base. `tests/Doroti.Tooling.Tests` still compares clean/cache-on bytes and now also checks port origins, the exact source-linked C diagnostic, the generated real-app dependency boundary, and a clean provider rebase.

`eng/doroti.ps1 release` builds and audits the SDK, compiles all P4 port manifests, emits normal and symbol packages from their effective projects, restores all generated packages from the local SDK feed, runs an external consumer, publishes and runs its trimmed self-contained single-file ReadyToRun image, reruns the provider rebase, installs/runs/uninstalls the project template, and audits package contents. `migration/releases/r10-beta.json` keeps clean-VM, injected-crash and release performance evidence explicitly `not-verified` until those external gates run.
